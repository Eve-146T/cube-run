# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Cube Run is a single-activity Android game: a minimalist 3-lane 3D endless runner built with **libGDX** and **Kotlin**. It is a privacy-respecting F-Droid-style app — only the `VIBRATE` permission, no network, no analytics, GPL v3. Runs on Android 9+ (minSdk 28): anything newer than API 28 must be guarded (`Haptics.predefined` shows the pattern), and `./gradlew lint`'s NewApi check enforces it.

## Build & run

Requires JDK 17, Android SDK platform 35, build-tools 35.0.0. The SDK location comes from `local.properties` (`sdk.dir=...`) or `$ANDROID_HOME`.

```bash
./gradlew assembleDebug     # -> app/build/outputs/apk/debug/app-debug.apk
./gradlew assembleRelease   # signed if keystore present, else unsigned (see signing)
./gradlew lint              # Android lint (the only static check; ObsoleteSdkInt is disabled)
./gradlew installDebug      # install to a connected device/emulator
```

There are **no unit tests** — `app/src/test` / `androidTest` do not exist. CI (`.github/workflows/build.yml`) builds a debug APK on branches/PRs and a signed release APK + GitHub Release on `v*` tags. `fastlane debug` / `fastlane release` are local conveniences wrapping the gradle tasks.

**Signing:** the release build reads `keystore.properties` (gitignored, local) or the `KEYSTORE_FILE`/`KEYSTORE_PASSWORD`/`KEY_ALIAS`/`KEY_PASSWORD` env vars (CI). With neither, the release APK builds **unsigned** rather than failing.

**Native libs:** the libGDX `.so` files are *not* checked in. The `copyAndroidNatives` gradle task extracts them from the `gdx-platform` artifacts into `app/libs/` (gitignored) before the JNI-merge step. A clean checkout therefore has no `libs/` until the first build.

## Architecture

The package root is `cube.run` (under `app/src/main/kotlin/`). **Build with JDK 17**: the machine default may be newer, so `JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64 ./gradlew ...` if the AGP/Kotlin toolchain complains.

**Startup chain:** `App` (Application) initializes the singletons — order matters, all are `init(context)`-style objects: `Scores`, `Settings`, `Progress`, `Haptics`, `SoundFx`. → `GameActivity` (a libGDX `AndroidApplication`) builds a `FrameLayout` stacking the libGDX GL surface under a `GameChromeView` HUD, then runs `CubeRun`.

**Two-thread model — this is the central design constraint.** The game (`Gdx3DGame`/`CubeRun` and everything in `game/`) runs entirely on the **GL thread**. The HUD (`GameChromeView` + `core/ui/*`, plain programmatic Android views) lives on the **UI thread**. They never touch each other directly: everything crosses through the `GameSession` interface, whose implementation `GameHostSession` marshals calls onto the UI thread (`activity.runOnUiThread`) and holds score/coins/boxes/over-state in atomics. Singletons read by the GL thread (`Settings`, `Scores`, `Progress`) expose `@Volatile` fields. When editing, keep this boundary: game code calls `session.addScore/banner/setCoins/gameOver`, never `chrome.*`. The one sanctioned "reverse" channel is polling: `Player` reads `Progress.skin` every frame so a shop change shows up live in the pre-run scene.

**Engine (`core/`)** — reusable for any 3D game:
- `Gdx3DGame` — the abstract base: `PerspectiveCamera`, lit `Environment`, `ModelBatch`, gradient sky, render order, juice (`shake`, `flash`, `burst3d`), auto-disposed model factories (`box`/`sphere`/`cylinder`/`cone`, `gdxHsv`; the allocation-free `hsvInto` is a top-level function in the same file). Subclasses implement `init` / `tick(dt)` / `renderWorldBatched` (queue boxes) / `renderWorld` (ModelBatch, for rotating/blended pieces only) / `renderHud`.
- `core/gfx/` — the heavy lifting the base delegates to: `BoxMeshKit` (unit-cube template + the Lambert light rig baked into vertex colours + the shared shader; its `environment()` MUST stay in sync with the light constants), `WorldBoxBatch` (every static box in ONE draw call with per-box fog toward `fogColor`; `box` axis-aligned, `boxSpin` rotated about Y for coins/pickups), `ShardSystem` (pooled cube-shard particles, one draw call), `TouchInput` (tap/drag/swipe → `TouchListener`), `PerfMonitor` (FPS digits + PERF logcat stats).
- `SoundFx` synthesizes all sound effects procedurally as PCM at startup (background thread), caches them as `.wav` in `cacheDir`, and plays via `SoundPool` — `play()` is a silent no-op until every sample finishes decoding. `Haptics` wraps `VibrationEffect`. `Palette` is an Android-side ARGB color helper.
- **Meta-progression:** `Progress` (prefs) holds the coin bank, the bubble stock, owned/equipped skins, `openBox()` (mystery-box rewards) and the only upgrades that exist: the **duration** of each power-up (`BUBBLE`, `MAGNET`, `MULT`, `JET`), ten manual levels each, each level just adding `Upgrade.step` seconds (`Upgrade.duration(level)`, `price(level)`). There are no passive upgrades (magnet radius, near-miss bonus, coin frequency are fixed constants in `CubeRun`/`Track`). The dev toggle calls `giveDevCoins()`. `Skins` is the skin table: shape (`CUBE`/`ORB`/`PYRAMID`) + colour mode, sampled per frame as pure functions of time.
- **Test tools (pre-run menu, left group):** the dev toggle (review cycle of `Sections.devPool` + unlimited coins) and the **section explorer** (`SectionsView`: every section as a `SectionThumbView` drawn from `Sections.preview`, tap one → `Settings.testSection`, process-scoped, the director serves it on loop until PLAY ALL). Both "review" modes announce section names and disable pickups (`Track.reviewing`).

**HUD (`core/ui/`)** — `Ui` holds the bright theme tokens (white cards, dark ink, gold coins, cyan bubble, purple boxes) and `UiKit` the widget helpers; keep new panels on them so everything reads as one screen. `PreRunMenu` = icon-only round buttons (sound / vibration / dev / section explorer left, skins / shop right — no labels), `ShopView` = the four duration upgrades with 10-segment level bars + bubbles, `SkinsView` = the wardrobe, full screen: the engine renders the cube itself on a dark stage and the page only frames it (name, price, dots, arrows, swipe = one step per gesture, EQUIP/BUY), `SectionsView` = the section explorer, `RunOverFlow` = the run-over sequence as separate focused screens: score (count-up, `CelebrationView` sunburst + confetti on a record) → mystery boxes (only if any) → GO AGAIN (RESTART / EXIT). `GameChromeView` composes them and owns the top score/best/coins/boxes/bubble-stock block.

**No text banners during play.** Pickups, smashes, streak milestones, tier unlocks and the bubble all speak through sound, a tinted flash, bursts and the FOV kick — `session.banner` is only used for section names in the review modes. Don't add gameplay text back; the user finds it in the way.

**Showcase stages are 3D and cross threads by state, not callbacks:** the HUD sets `Stage.mode` (`BOX` for the mystery-box page, with `Stage.openRequests`; `SKINS` for the wardrobe, with `Stage.previewSkin`) and `CubeRun.tick` hands the frame to `GiftStage` (dark backdrop, fixed camera, the gift built from batched boxes, shake → lid launch → gold fountain; rolls `Progress.openBox()` on the GL thread and reports through `session.boxOpened(kind, amount)` → `RunOverFlow.onBoxOpened`) or to the wardrobe branch (`Player.showcase` poses the previewed skin at the origin; `Player.wantedSkin` prefers `Stage.previewSkin` over the equipped skin). Keep it that way — no listeners across the GL/UI boundary.

**Game (`game/`)** — `CubeRun` is the conductor (run state, input routing, collision + pickups + scoring, camera); the pieces are:
- `Track` — the director + lane-walk (see below); owns `rows`, spawning, row motion and obstacle animation.
- `Obstacles.kt` — `Ob`/`Coin`/`Row` data, `ObType`/`ObAnim`/`Pickup` constants, and `ObstacleFactory` (the visual language: fixed hue offsets per verb).
- `Sections.kt` — `Step` codes + `Sect` + the `Sections` library (tiers, weights, `devPool`, `tierFor`).
- `Player` — lane/jump/roll physics, pose, skin models + glow shell + trail.
- `Shield` — the bubble (timer, sphere). `PowerUps` — the timed magnet / 2× / jetpack timers and every HUD timer bar (the shield's included). `Difficulty` + `FireBoost` — speed/tier axis and the opening boost button. `Scenery` — floor tiles, posts, wind streaks, and the `Fog` constants. `GiftStage` — the run-over 3D box.

## CubeRun gameplay model (read before touching `game/`)

- **The track is a guaranteed-solvable "lane-walk":** a continuous stream of rows where the safe lane (`curSafe`) moves by at most one between consecutive rows (`Track.walkTo`). Hand-authored patterns (`Sect`, e.g. SLALOM, GAUNTLET, TAR PITS, MACHINE ROOM) are step-code arrays decoded by `Track.spawnStep`; the `pickSection` director stitches them with **tier-gating** (harder sections unlock as difficulty rises) and random **mirroring**. Spacing/reachability is enforced by the walk, so sections are pure shapes. The pre-run **dev-mode toggle** (`Settings.devMode`, the `</>` button) makes the director cycle `Sections.devPool` (the sections under review, currently ids ≥ 36) in order — no intro/breathers/pickups — and banner each section's name as its first row nears the player; the cycle cursor survives in-task RESTARTs. The **section explorer** (grid button) does the same for one chosen section on loop. New sections need a `Sections.preview` decode only if they use a new step code (the thumbnail derives from the codes).
- **Step codes** (`Step`): dodge / feint / slider / jump-wall / duck-bar / empty / hurdle-window / duck-window / hurdle-gate / pincer, plus the animated kinds: `VD` tar pit (a flat void: be airborne over it — any jump clears it, rolling doesn't), `PS` pistons (pump out of the floor per lane, phase-staggered: jump, or run over a sunk one), `SW` sweeper (a low beam gliding across all lanes: jump), `st(l)` stompers (slamming blocks on the two lanes beside the safe one), `vw(l)` tar window. Collision types stay `DODGE`/`JUMP`/`DUCK` (+ `DECO` for tar rims, never collides); animated obstacles mutate `x`/`cy`/`sy`/`clear` each frame in `Track.scroll`. Collision is resolved per-row in `CubeRun.tick` against the cube's lateral gap, bottom, and (roll-tucked) head height — partial-width JUMP/DUCK pieces only count when the cube laterally overlaps them. Jump-verb rows (`Step.isJump`) get `jumpRecoverGap` after them.
- **Platforms (`pl`/`pf` codes, `ObType.PLAT`)** are the "trains": one segment per row (`dodgeGap` deep, front at the row's z, `PLAT_TOP` high), ramped (drawn as steps) whenever the lane had no platform on the previous row, flat continuations otherwise. `pl` blocks the other lanes (mandatory climb), `pf` leaves them open (the high road). `CubeRun.groundAt` gives the walkable height under the cube (linear along the ramp); `Player.update` climbs ramps, drops off ends into a fall, lands on roofs, and reports `EV_SIDE_HIT` when a whole platform side arrives at ground level (fatal, or the bubble hoists you up). Authoring rule: never put another obstacle in a platform's lane on the same row. Roof coins are always laid.
- **Goodies ride the walk lane:** coin trails (arc over jump rows, low under duck rows, a line after everything else — `Track.layCoins`), and pickups between rows (`Track.layPickup`, spaced ≥14 rows apart): timed power-ups — MAGNET (huge pull), MULT (2× score), JET (fly at `Player.FLY_Y` above everything along an air coin line: `Track.liftCoins`/`dropCoins`, `airCoins`, then a short `jetGrace` landing) — a floating bubble (instant shield), and the mystery box, which is deliberately rare (`boxSpacing` ≥ 90 rows). Pickups are built from spun boxes in `CubeRun.renderPickup`; each timer's length comes from its `Progress` upgrade.
- **The bubble shield** (`Shield`): double-tap in-run to spend one from stock (or grab a track pickup). Timed (`Progress.BUBBLE.duration`). It absorbs exactly ONE crash: `CubeRun.smash` shatters the row you hit, dissolves every obstacle in a ~2 s breather zone ahead, and pops the bubble — no chaining, no invulnerability after the breather. Keep it that way.
- **Difficulty is one axis:** `Difficulty.diff` in 0..1 drives speed (`minSpd`..`maxSpd`, flattening past the `blueLine` cruise) and the unlocked section tier (`Sections.tierFor`; tier 3 starts at 0.60, just past a maxed fire boost). A tier unlock banners "LEVEL n".
- **Juice budget:** screen shake is deliberately rare and small (crash 0.5, smash 0.22, nothing else). Prefer flashes, bursts and the camera FOV kick (`fovKick`) over shake.
- **Control schemes:** classic single-flick swipe vs. `Settings.smoothControl` (positional steering). The smooth-control UI is behind `Settings.SMOOTH_CONTROL_UI` (currently off, and its toggle is no longer built by the HUD).

### Performance & lifecycle gotchas

- `tick()` is a per-frame hot path: it is written allocation-free. `hsvInto` writes into an existing `Color`, a single `tmp` `Vector3` is reused per class. Preserve this — don't allocate per frame in the loop (row/coin lists are allocated at spawn time only).
- **All world geometry (tiles, posts, obstacles, coins, gift boxes, wind streaks) renders through the batched `WorldBoxBatch` pass** — one draw call, fog included; `Tile`/`Post`/`Ob`/`Coin` are plain data, no `ModelInstance`s. Only the player/shell/shadow, the bubble sphere and bubble pickups go through `ModelBatch`. Don't add per-row `batch.render(...)` calls back: 100+ ModelBatch renderables cost ~7 ms/frame on a low-end phone, the batched pass ~1 ms. The distance fog (`Fog.start`/`Fog.end` < `|Track.spawnZ|`) is also what hides row spawn-in — keep `spawnZ` beyond `Fog.end`. The batch cap is 480 boxes; obstacles are queued first so overflow drops scenery, never gameplay.
- After `gameOver()` the render loop keeps running for the death animation. Guard all gameplay mutation with `session.isOver` / the local `dead` flag (`CubeRun.live()`).
- **RESTART finishes and relaunches the activity** (`finish()` + `startActivity`), it does **not** call `recreate()`. libGDX only disposes native GL/mesh resources when the activity truly finishes; `recreate()` would leak them. Keep this if you touch the game-over flow in `GameOverCard`.
- **Testing on a device:** the app is debuggable, so save data can be seeded with `adb shell run-as cube.run` (edit `shared_prefs/progress.xml` for coins/bubbles/upgrades, `scores.xml` for the best) — force-stop the app first, it caches prefs in memory. To exercise rare pickups, temporarily raise the chances / lower the spacings in `Track.layPickup` (and pin `pickupX` to lane 1) — and revert before committing. `adb exec-out uiautomator dump /dev/tty` gives button bounds for scripted taps.
